# Live system

Runtime component of [resolution_alpha](../README.md). Discovers every open recurring crypto interval market on Kalshi (no hardcoded BTC/ETH list), monitors each one as it approaches close, and buys the favored side late in the window when the order book supports it. **Defaults to dry-run** (logs intended trades, places nothing). See Status below.

> **Layout:** this folder holds only the launcher scripts (`start_live.*`, `stop_live.*`, `pnl_killswitch.*`) and `.env`, matching `../../btc_implied_prob/live` and `../../golf_field_alpha/live`. Every module named below (`runner.py`, `discovery.py`, `probability.py`, `config.py`, …) lives one level up in `../`. The launchers `cd` into this folder, then run `../runner.py` with the repo-root `.venv` and the experiment root on `PYTHONPATH`.

Runs on `asyncio` and talks to Kalshi's authenticated websocket (`ws_feed.py`) for order books and, for BTC/ETH, the actual settlement index — falling back to REST polling (the original design) wherever the socket has no data yet, e.g. no credentials configured, or another underlying with no known index id. Order placement is unchanged either way: `order_manager.py` wraps `KalshiTradingClient` from `prediction_market_scraper/Clients/Kalshi/live_execution.py`, the same authenticated REST trading client as before.

## Pre-flight checklist (read this before running, especially before a real-money run)

1. **Check what's already running.** `ps aux | grep python` (or Task Manager) — a stray previous instance left running will duplicate discovery/trading against the same account. Kill it before starting a new one.
2. **Check `.env`.** `RESOLUTION_ALPHA_DRY_RUN` — confirm it's set to the value you actually intend (defaults to `true`/paper if unset or missing entirely, so a *missing* var is safe but a stray `false` left over from a previous session is not). `KALSHI_API_KEY_ID`/`KALSHI_PRIVATE_KEY_PATH` — must both be set for the websocket feed and for real trading; **use forward slashes in the path even on Windows** (see the git-bash gotcha further down — a backslash path gets silently mangled by `source .env` and used to fail with no log output at all before that was fixed).
3. **Re-read "Known gaps" below in full**, not just the Status line — it's the up-to-date list of what has and hasn't been validated. In particular: fill/liquidity economics at real trading size have never been backtested (no historical order book exists), and `MAX_CYCLE_CONTRACTS` is a coarse global cap, not a precise per-market budget.
4. **Sanity-check the sizing config against real account balance** (`config.py` / `.env` overrides). Position sizing is dynamic (fractional-Kelly off edge + balance, see `runner.py`'s `_kelly_contracts`) as of 2026-08-06, but `MAX_CONTRACTS_PER_MARKET` and `MAX_CYCLE_CONTRACTS` are still hard ceilings on it -- `MAX_CONTRACTS_PER_MARKET` × the number of markets that can plausibly clear the entry window inside one `MAX_CYCLE_CONTRACTS` bucket, at up to $1/contract, is the realistic worst-case exposure per 15-minute bucket if Kelly ever sizes up to the ceiling (e.g. on a very cheap, very high-confidence contract). Check `client.get_balance()` and make sure that ceiling is a number you're actually fine risking, especially before liquidity economics at size have been validated. `RESOLUTION_ALPHA_KELLY_FRACTION` (default 0.10) controls how aggressively Kelly sizes relative to that ceiling.
5. **Prefer starting in dry-run first**, even if the end goal is real money, after *any* code change — the per-market re-buy bug and the busy-loop hang (see Known gaps history) were both only caught by watching a live dry-run sit inside a real market's entry window, not by static review or the backtest.
6. **If about to flip to real money for the first time in a while**, re-verify order placement with a tiny real order before trusting it with strategy-driven size — see "Known gaps" for exactly what was and wasn't validated this way on 2026-08-06, and don't assume a resting-limit-order test is risk-free: **check the live order book first**, since a price you expect to be non-marketable can still cross and fill instantly on a thin/extreme-strike market (this happened during that verification and is documented below).
7. **Watch the first few real cycles live** (tail the log) rather than starting it and walking away — the fastest way anything wrong here shows up is a `LIVE ORDER:` log line you didn't expect.

## What's actually running here (confirmed against the live API on 2026-08-05 unless noted)

- `discovery.py` — scans `category="Crypto"` series, keeps ones with `frequency` in `("fifteen_min", "thirty_min", "hourly")`, and pulls every currently-open market instance in them. Confirmed live: ~1,660 open markets across BTC, ETH, SOL, XRP, DOGE, BNB, HYPE, NEAR, ZEC at 15m and 60m cadences. No 30m crypto series existed at test time; the frequency is kept in the filter for when one appears. Retries per-series on HTTP 429 (added after a live dry-run + `../backtest.py` run concurrently exhausted Kalshi's public rate limit and killed a discovery cycle) instead of aborting the whole discovery pass.
  - "Range"-type markets (`strike_type == "between"`) are skipped — v1 only trades single-strike above/below markets.
  - **Scoped to trusted underlyings by default.** `find_active_markets` is called with `config.TRUSTED_SETTLEMENT_UNDERLYINGS` (BTC/ETH) unless `RESOLUTION_ALPHA_TRADE_UNSAFE_MARKETS=true`, so the ~20 other live crypto series aren't discovered at all — no spot poll, no order-book subscription, no per-tick evaluation for markets the untrusted-underlying gate would only skip anyway. Turn the flag on to scan and trade every underlying (re-exposes Coinbase-proxy basis risk — see Settlement mechanics).
  - Kalshi pre-lists hourly markets days ahead of their actual close; `interval_minutes` is read from the series' declared `frequency`, not derived from `close_time - open_time` (that delta reflects listing lead time, not settlement cadence, for these).
- `spot_feed.py` — polls Coinbase's public spot endpoint per underlying (no auth needed) and keeps a rolling price history. **A proxy, not the real settlement source** — used for every underlying except BTC/ETH, which get the real thing via `ws_feed.py` instead (see "Settlement mechanics" below).
- `ws_feed.py` — **new.** Owns the websocket connection to `wss://api.elections.kalshi.com/trade-api/ws/v2` and maintains two pieces of state from it:
  - `orderbook_delta` channel, reconstructed from an initial snapshot plus signed quantity deltas per price level, exposed as `get_orderbook_fp(ticker)` in the same shape `fetch_orderbook()` returns. Subscribed tickers are kept in sync via `update_subscription` add/delete calls rather than tearing down the connection each cycle -- but scoped to markets within `ORDERBOOK_SUBSCRIBE_LOOKAHEAD_SECONDS` of `close_time` (config.py), not every open market. Only a handful of the ~1,600+ open markets are ever actually close to closing at once, so subscribing to all of them would be pure waste.
  - `cfbenchmarks_value` channel for `index_ids=["BRTI", "ETHUSD_RTI"]` — Kalshi's actual settlement index, not a proxy. Only wired up for these two confirmed ids; discovering more (SOL, XRP, DOGE, ...) needs the `indexlist` action against a live connection, not done here.
  - Needs `KALSHI_API_KEY_ID`/`KALSHI_PRIVATE_KEY_PATH` (every Kalshi websocket subscription requires a signed handshake, even for public market data). Without them, logs one warning and the whole feed stays permanently disconnected — `runner.py` falls back to REST/Coinbase for everything, i.e. the pre-websocket behavior.
  - **Confirmed working against the live socket on 2026-08-05**: connects, authenticates, subscribes to both channels, receives snapshot/delta/index messages, and holds a stable connection across multiple discovery cycles. Three real bugs were caught and fixed getting there: an empty-`market_tickers` subscribe getting rejected by Kalshi, a Windows-path/bash-`source` gotcha (see below) silently breaking key loading, and a subscription-sync loop that busy-spun with no `await` once steady-state — starving the whole single-threaded event loop and hanging the live process for minutes with no error logged. See "Known gaps" for what's still unverified.
- `probability.py` — z-score-style resolution probability, with a settlement-window-aware regime for the last 60 seconds (see below). Calibration checked against 24h of real settled markets — see `../README.md`'s Backtest plan results.
- `orderbook.py` — walks the order book (from `ws_feed` if available, else a fresh REST `fetch_orderbook` call) to get a realistic fill price/size for a target position, instead of assuming a fill at the best displayed price.
- `fees.py` — exact fee formula (`0.07 * contracts * price * (1-price)`, rounded UP to the nearest **$0.0001**, matching the "quadratic" fee type Kalshi reported for these series). Confirmed exactly against three real fills on 2026-08-06. An earlier version rounded up to the nearest whole cent instead, which imposed a hidden ~$0.01 floor on every trade's estimated fee and was silently killing edge on small/cheap-contract trades — see Known gaps.
- `order_manager.py` — dry-run by default; places real orders only when `RESOLUTION_ALPHA_DRY_RUN=false` and Kalshi credentials are set. Also exposes `get_balance_dollars()` (real account balance, used for Kelly sizing below).
- `runner.py` — the main loop, now `asyncio`-based. Refreshes spot/index data continuously for every discovered underlying (so volatility history is warm before a market enters its trade window, not starting from zero with 90 seconds left), and only evaluates/trades markets inside `ENTRY_WINDOW_SECONDS` of `close_time`. Position sizing is dynamic as of 2026-08-06: `_kelly_contracts` sizes each trade as a fraction (`RESOLUTION_ALPHA_KELLY_FRACTION`, default 0.10) of the full-Kelly stake implied by that trade's edge and the current account balance, floored to a whole contract count and clipped by `MAX_CONTRACTS_PER_MARKET`/`MAX_CYCLE_CONTRACTS` (renamed from a fixed `TARGET_CONTRACTS` -- those are now hard ceilings the dynamic size gets clipped to, not the size itself). Bankroll is fetched once per 15-minute cycle and decremented locally after each fill, not re-queried on every tick.

## Settlement mechanics (resolved from a live market's contract rules, not guessed)

Pulling `KXBTC15M-26AUG041315-15` live returned this in `rules_primary`:

> If the simple average of the sixty seconds of CF Benchmarks' BRTI before [close] is at least the simple average of the sixty seconds of CF Benchmarks' BRTI before [open], then the market resolves to Yes.

So settlement is a **60-second trailing average** of CF Benchmarks' Real Time Index ending at `close_time`, not an instantaneous last-tick price, and the strike (`floor_strike`/`cap_strike`) is itself a 60-second average captured at open. This resolves an open question from the main README and changes the probability model near expiry: once inside the last 60 seconds, part of the settlement average is already realized and only the remaining seconds are still stochastic — variance shrinks faster than a naive "time to close" model would suggest. `probability.py` models this explicitly (see its docstring); the blend/variance formula there is a reasonable approximation, not a validated one — flagged for the backtest.

**Spot proxy basis risk (resolved for BTC/ETH, open for everything else):** CF Benchmarks' index isn't freely available over REST, but Kalshi's own websocket streams it directly via `cfbenchmarks_value` — `ws_feed.py` subscribes to `BRTI` (BTC) and `ETHUSD_RTI` (ETH) and feeds those real index ticks into `probability.py` in place of Coinbase spot for those two assets. Every other underlying (SOL, XRP, DOGE, BNB, HYPE, NEAR, ZEC, ...) still uses `spot_feed.py`'s Coinbase proxy and still carries this basis risk — extending coverage needs the `indexlist` websocket action to discover more index ids, not done here.

## Order book mechanics (confirmed against a live snapshot, both REST and websocket)

`fetch_orderbook(ticker)` (REST) returns `{"yes_dollars": [[price, qty], ...], "no_dollars": [[price, qty], ...]}` — resting bid levels only, sorted ascending by price, no separate displayed ask book. `ws_feed.get_orderbook_fp(ticker)` reconstructs the same shape from `orderbook_delta` snapshot + delta messages instead of polling. Buying YES means crossing resting NO bids (a NO bid at price `p` is a YES ask at `1-p`), and vice versa. `orderbook.walk_book` implements this and reports partial/zero fills honestly when depth is thin, rather than assuming the quoted best price fills any size — unchanged regardless of which source the book came from.

## Running it

```
cd expirments/resolution_alpha/live
pip install -r ../requirements.txt     # or use the repo-root .venv (see below)
cp .env.example .env   # edit, then export the vars into your shell
./start_live.sh        # or start_live.bat on Windows; runs ../runner.py detached
```

`start_live.*` uses the repo-root `.venv` (`python -m venv .venv` at the repo root, then `.venv/bin/pip install -r expirments/resolution_alpha/requirements.txt`), falling back to PATH python if it's missing. To run the loop in the foreground instead: `cd ..` then `python runner.py`.

Defaults to dry-run — every intended trade is logged (`[DRY RUN] would BUY ...`), nothing is placed. To place real orders: set `RESOLUTION_ALPHA_DRY_RUN=false` and `KALSHI_API_KEY_ID` / `KALSHI_PRIVATE_KEY_PATH`. **Don't do that yet** — see Status. Without those two credentials the websocket feed stays disabled and everything runs over REST/Coinbase, same as before `ws_feed.py` existed.

Tunable thresholds (entry window, min probability, min edge, position size, poll cadence) are environment variables documented in `config.py` and `.env.example`.

**Lightweight mode** (`RESOLUTION_ALPHA_LIGHTWEIGHT_MODE=true`, off by default): sleeps through most of each 15-minute interval instead of running continuously, waking only for the last `RESOLUTION_ALPHA_LIGHTWEIGHT_WAKE_WINDOW_SECONDS` (default 180s / 3 minutes) before each interval's close. That window has two phases: the first half (down to `RESOLUTION_ALPHA_LIGHTWEIGHT_TRADING_WINDOW_SECONDS`, default 90s before close) only runs discovery + spot/index polling + order-book subscriptions, to warm up volatility history and book state; the second half runs full trade evaluation, same as with the mode off. Suppresses all logging for as long as the mode is on. Still trades away most of the loop's visibility and gives volatility history less lead time than a fully continuous run, so treat it as an explicit opt-in for minimum footprint, not the default posture.

**Windows/git-bash gotcha, hit and fixed on 2026-08-05:** `KALSHI_PRIVATE_KEY_PATH` as a `D:\...\...` backslash path silently breaks when the `.env` file is loaded via `set -a; source .env; set +a` in bash — unquoted backslashes are interpreted as escape characters and stripped, turning `D:\Files\Code\...` into `D:FilesCode...`. `_load_private_key` then fails with a plain `FileNotFoundError` that (before this was also fixed) died silently inside the websocket task with no log line at all, since it wasn't the "credentials missing" case the code was already handling. Use forward slashes in the path (`D:/Files/Code/.../KalshiKey.txt`) — Windows and Python both accept them, and bash won't touch them.

## Emergency stop

**Stop new trades** — kill the process. This is the real kill switch; nothing else in the loop can place an order once the process is dead.

```bash
./stop_live.sh                                       # or stop_live.bat -- reads .runner.pid / .killswitch.pid
# or manually:
ps aux | grep "runner.py" | grep -v grep            # find PID
kill <PID>
```

**Cancel any orders still resting** (not yet filled) — killing the process does *not* do this automatically:

```bash
cd expirments/resolution_alpha        # modules live at the experiment root now
set -a && source live/.env && set +a
python -c "
from kalshi_gateway import KalshiTradingClient
client = KalshiTradingClient()
for o in client.get_orders(status='resting')['orders']:
    print('canceling', o['order_id'], o['ticker'])
    client.cancel_order(o['order_id'])
"
```

**What this doesn't do:** `buy_favored_side` places a *marketable* limit order (priced at the walked-book fill price), so in practice most orders fill immediately rather than resting — confirmed live on 2026-08-06 (see Known gaps), where a test order meant to be non-marketable filled instantly instead. By the time you notice something's wrong, there's often nothing left resting to cancel. There's no "undo" for an already-filled order — the only way out of an unwanted position is placing an offsetting order (sell what you hold), and Kalshi may or may not have a counterparty for that at a given moment. Treat killing the process as the primary safeguard, not order cancellation.

## Known gaps / things to fix before trusting this with money

- **~~Would re-buy the same market on every poll tick for its whole entry window~~ — found live, fixed.** `evaluate_and_maybe_trade` had no per-market "already traded" tracking, only a global `MAX_CYCLE_CONTRACTS` budget across the whole 15-minute bucket. Observed live on 2026-08-05: `KXXRP15M-26AUG052000-00` cleared the edge threshold on 9 consecutive ~2.5s ticks as its book thinned into close (fill price fell from 0.86 to 0.44 as the model's confidence rose toward 1.0 -- a real, sharp illiquidity effect matching the strategy's core thesis, not bad data), and `runner.py` logged a `[DRY RUN] would BUY 10 NO` on every single one of those ticks. With real money this would have meant 9x+ oversizing one position instead of the intended one-shot `TARGET_CONTRACTS`. Fixed by tracking a per-cycle `tickers_traded` set and skipping any market already bought this cycle -- **this is exactly the kind of bug dry-run exists to catch**, and it would not have been visible from the backtest (which only checks probability calibration, not repeated-evaluation behavior) or from a short smoke test that doesn't sit inside one market's live entry window long enough to see it repeat.
- **~~Order-placement endpoint unverified~~ — verified 2026-08-06, and a real bug found and fixed along the way.** Checked `KalshiTradingClient`'s order endpoints against Kalshi's current published API docs (docs.kalshi.com/api-reference/orders/*): `POST`/`DELETE /portfolio/events/orders` (create/cancel) and `GET /portfolio/orders` (list) are all correct — the earlier note here claiming a `/portfolio/orders` vs `/portfolio/events/orders` mismatch was itself wrong, not a real bug. What *was* a real bug, caught during this check: Kalshi's order `side` field is only ever `"bid"` (buy YES) or `"ask"` (sell YES, i.e. economically buy NO at `1 - price`) — "for event markets, this refers to the YES leg only." `order_manager.buy_favored_side` was passing the model's favored side (`"yes"`/`"no"`) straight through as the API's `side` field, which is a different vocabulary entirely; a `"no"` order would have been rejected outright (invalid enum) or worse. Fixed in `order_manager.py` via `_to_api_order`, which translates `("no", price)` → `("ask", 1 - price)`. Confirmed against the live account with a real order: a 1-contract BID (buy YES) test at $0.01 on `KXHYPED-26AUG0601-T93.9999` **filled instantly** (cost $0.0107 incl. fee) rather than resting, because that price was actually marketable on that market's thin, extreme-strike book (yes_ask was $0.01 with ~22k contracts offered) — a reminder that "far from market" needs to be checked against the actual book, not assumed. That fill is real and left a trivial (~1 cent) open YES position expiring within the hour, essentially certain to resolve NO. The `"ask"`/buy-NO path was verified by code+docs review, not with a second live fill, to avoid compounding incidental positions. Order-cancel and get_orders/get_positions were also exercised live and returned the expected shapes.
- **~~Fee estimate rounded up to the nearest whole cent, not the actual granularity~~ — found and fixed 2026-08-06.** `fees.py`'s formula was right (`0.07 * contracts * price * (1-price)`) but the rounding was `ceil(raw * 100) / 100` -- up to the nearest **cent**. Confirmed wrong against three real fills the same day (e.g. a 1-contract $0.01 trade had an actual fee of $0.0007, not the $0.01 the old formula would estimate -- a 14x overestimate). This put a hidden ~$0.01 floor under every trade's estimated fee regardless of the real amount, which silently failed the `MIN_EDGE_DOLLARS` check for small/cheap-contract trades that were actually profitable -- exactly the trades a small account or a Kelly-sized strategy makes most of. Fixed to round up to the nearest **$0.0001**, which matches all three real fills exactly.
- **~~Fixed position size (`TARGET_CONTRACTS`) doesn't scale~~ — replaced with dynamic Kelly sizing 2026-08-06.** Every trade used to be the same fixed contract count regardless of edge size or account balance, which doesn't make sense as the account grows or shrinks, and doesn't size up when a trade's edge is unusually large. `runner.py`'s `_kelly_contracts` computes the full-Kelly stake `(q - p) / (1 - p)` implied by a trade's model probability and price, scaled by `RESOLUTION_ALPHA_KELLY_FRACTION` (default 0.10, i.e. 1/10 Kelly -- deliberately conservative given how little live validation this strategy has, see the calibration caveats above and in `../README.md`) and the current account balance (fetched once per 15-minute cycle, decremented locally per fill within it). Still hard-capped by `MAX_CONTRACTS_PER_MARKET`/`MAX_CYCLE_CONTRACTS` (the renamed former `TARGET_CONTRACTS`/`MAX_CYCLE_CONTRACTS`) so a bad probability estimate can't size up an arbitrarily large position.
  - **~~First version sized off a single top-of-book price, which breaks once liquidity thins~~ — found and fixed same day, before ever running with real money.** The first cut peeked the best price for 1 contract, ran the Kelly formula once off that price to get a fixed target size, then walked the book to that target and checked the *average* edge across it. Two failure modes: a thinning book drags a good near-touch trade's average edge below `MIN_EDGE_DOLLARS` by mixing in bad deep-book prices (rejecting a trade that should partially execute), or a single very deep level (Kalshi order books can have thousands of contracts resting at one price) blows straight through the Kelly cap and gets rejected *entirely* instead of taking the Kelly-sized slice of it. Fixed in `_size_for_edge`: walks the book contract-by-contract (binary search within each price level, not all-or-nothing per level), re-checking both the edge threshold and the Kelly cap *at the cumulative average price so far* at each step, and stops at the exact contract where either constraint first fails -- since ask price is non-decreasing as the book is walked, both checks are non-increasing in cumulative size, which is what makes stopping at the first failure (rather than scanning further) correct. Verified with synthetic book scenarios covering both failure modes (thin/degrading book, abundant depth at one price with a small bankroll) plus a 60s live dry-run smoke test -- not yet exercised against a real thin book live, only synthetically.
- **~~No sanity check between the model's claimed probability and the market's own price~~ — found live and fixed 2026-08-06, real money involved.** `KXXRP15M-26AUG060245-45`: spot was essentially equal to strike with 53s left (about as close to a coin flip as this strategy ever sees), the market's own top-of-book price implied ~72% confidence in the favored side, but `probability.py` said 98.56% -- a 26-point gap versus every other real trade that session clustering under 10 points. Root cause: in the last 60s, `sigma_used` is driven by *recent realized* volatility; a quiet recent stretch produces a tiny sigma estimate, and a tiny sigma turns even a noise-level spot/strike gap into an extreme z-score. Most likely lost (reconstructed from balance math, no direct per-market settlement record available). Fixed with two gates in `evaluate_and_maybe_trade`, both compared against the market's own top-of-book price, not the model's claim: (1) `MIN_MARKET_IMPLIED_PROBABILITY` (default 0.80) -- hard refuse to trade if the market itself isn't already at least this confident in the favored side; (2) `MAX_TRUSTED_EDGE_PROB` (default 0.12) -- even above that floor, cap the probability used for edge/Kelly sizing at `market_price + this`, so an implausible divergence still shrinks (rather than maxes out) the position instead of being rejected outright. Verified with a synthetic replay of the exact incident (spot=strike, model=98.56%, market=72%) -- correctly blocked by gate (1) alone.
  - **Related, same incident: the log line's 2-decimal spot/strike formatting made this hard to diagnose.** `spot=1.05 strike=1.05` in the log reads as "identical" for an asset like XRP that actually trades in fractional cents, hiding exactly the information needed to tell a genuine near-the-money situation from a real gap -- matters far less for BTC/ETH-scale prices but costs nothing to fix uniformly. Bumped to 6 decimals (`spot=%.6f strike=%.6f`). This was a diagnostic-precision issue in the log line only -- the actual probability math in `probability.py` always used full float precision for spot/strike, never rounded.
- **~~Order price rejected (400 invalid_price) on every multi-level fill~~ — found live and fixed 2026-08-06, real money involved, no losses.** Once Kelly sizing started producing multi-contract trades that routinely spanned more than one order-book price level (e.g. `KXETH15M`, `KXBTC15M`, `KXXRP15M` all in one session), every single order placement attempt failed: `400 {"error":{"code":"invalid_price","message":"invalid price"}}`. Root cause: `order_manager.buy_favored_side` was submitting `fill.avg_price` -- a *blended average* across however many book levels got walked -- as the order's limit price, and Kalshi rejects any price that isn't tick-aligned (`price_level_structure: "linear_cent"`, whole cents, confirmed by reproducing the exact error against a live test order at a fractional-cent price, and confirming clean whole-cent prices filled fine). Fixed by submitting the *boundary* (worst-acceptable) price of the walked fill instead -- `fill.levels_used[-1][0]` -- which is always one of the book's own already-cent-aligned levels; Kalshi's matching engine walks the book itself from there and fills each contract at its own (better-or-equal) price, same as the maker/taker mixed-price fills already observed on this account. No money was lost from the bug itself (every rejected attempt failed before any fill), but it did produce an alarming symptom: because `tickers_traded` was only updated on a *successful* placement, the same few markets got silently re-attempted (and re-rejected) on every ~2.5s tick for the rest of their entry window -- visually identical to the per-market-re-buy bug from 2026-08-05, just from a different root cause. Fixed alongside: `tickers_traded.add(...)` now happens unconditionally before the placement attempt, so any failure (this one or a future one) stops retrying that market for the rest of the cycle instead of hammering it. Verified: reproduced the exact 400 against a live test order, confirmed whole-cent prices fill live, and a synthetic unit test confirms the code now submits the tick-aligned boundary price (0.99) rather than the fractional blended average (0.9775) for a deliberately multi-level book.
- **Fill/liquidity economics still unvalidated against history.** The probability model's calibration has been checked against 24h of settled markets (see `../README.md`'s Backtest plan) and looks strong, but whether the order book actually supports the intended size at a good price near expiry has only been observed live in dry-run, never backtested — Kalshi's REST API has no historical order book, so this needs `ws_feed.py`'s live book recording to accumulate real data over time.
- **CF Benchmarks index coverage is BTC/ETH only.** Every other underlying still has Coinbase-proxy basis risk (see above).
- **`MAX_CYCLE_CONTRACTS` is a coarse global cap** on a 15-minute wall-clock bucket, not a precise per-market-interval budget — imprecise for hourly markets, which span four such buckets.
- **No resolution/P&L logging yet.** The runner logs each evaluation and trade decision but doesn't yet record resolution outcomes or reconcile fills — needed to turn live runs into backtest-quality data.
- **Websocket reconnect/backoff is implemented but has only been exercised over one continuous live session** — a real network drop or Kalshi-side disconnect hasn't been observed yet to confirm the reconnect path resubscribes cleanly.

## Status

Live loop running on Kalshi's authenticated websocket for order books and BTC/ETH settlement index, REST/Coinbase fallback for everything else — confirmed connecting, authenticating, subscribing, and staying up across multiple discovery cycles against the live socket on 2026-08-05, after finding and fixing four real bugs along the way (an empty-`market_tickers` subscribe getting rejected, the Windows-path gotcha above, an event-loop-starving busy-loop in the subscription sync task, and the per-market re-buy bug above -- the last one caught by dry-run observing a real market's full entry window, not by static review). Probability-model calibration checked against 24h of real settled-market outcomes and looks strong at the >=97% threshold this strategy trades on (see `../README.md`). Order placement itself (endpoint, request schema, the yes/no-to-bid/ask translation) was verified against the live account on 2026-08-06, including a real fill and a real bug fix (see Known gaps) — this was the last major unverified piece of the execution path. **Still not validated: fill/liquidity economics at real trading size** (no historical order book exists to backtest this against — only ever observed live in dry-run, never at the size/frequency a real run would trade). Treat that specific gap as the reason to watch a real-money run closely rather than walking away from it, not as a reason to stay in dry-run forever.
